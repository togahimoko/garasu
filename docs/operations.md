# Эксплуатация и выпуск

## Проверки перед выпуском

Требуются Python 3.10+ и PyYAML, для проверки Mihomo — актуальное локальное ядро. Работать рекомендуется в отдельной копии репозитория.

```bash
python3 -m unittest discover -s tests -v
python3 scripts/audit_public_exposure.py
python3 scripts/audit_rules.py --check
```

Нативную конфигурацию Mihomo дополнительно проверяют с **синтетическими узлами** и временным каталогом: шаблон Remnawave содержит места вставки узлов и не предназначен для непосредственного запуска без их генерации. Тестируют 0, 1 и несколько узлов, загрузку всех MRS, DNS, отказ узла и отсутствие скрытого перехода внешнего трафика в DIRECT.

## Обновление правил

`scripts/refresh.py` обращается к внешним источникам и **изменяет файлы** после проверки данных, поэтому его следует запускать сначала в отдельном рабочем каталоге с резервной копией и проверкой diff. Он также обновляет совместимые URL и манифесты для старых клиентов.

```bash
python3 scripts/refresh.py
python3 scripts/audit_rules.py --check
```

Далее пересобираются MRS:

```bash
python3 release/mihomo/build.py --core /path/to/mihomo \
  --source-root . --output /tmp/garasu-mrs-next \
  --source-commit YOUR_COMMITTED_SOURCE_SHA
```

Проверяются SHA-256, число правил, корректность `format: mrs`, URL каждого провайдера и загрузка в реальном ядре. Нельзя публиковать MRS от другого снимка исходных списков. Существующая ветка `staging` является источником ссылок тестовых профилей; при утверждении релиза ссылки следует закрепить за проверенным коммитом.

GitHub Actions для обновления и публикации не используются в рефакторинговой ветке. Автоматическая регенерация исходных файлов и бинарных MRS вне GitHub Actions пока не настроена; клиентские интервалы обновления не заменяют сборку новых данных на сервере.

## Remnawave

Шаблоны в панели должны быть установлены отдельно; коммит в GitHub не меняет шаблоны, хранящиеся в Remnawave.

1. Экспортировать действующие SSR, шаблоны и настройки подписки.
2. Создать **отдельный** тестовый MIHOMO-шаблон `Garasu`, не заменяя действующий у платных пользователей.
3. Проверить выдачу на выделенной тестовой подписке через `release/remnawave/srr-test.json` и User-Agent `garasu-test-mihomo`.
4. Проверить персональную VLESS/REALITY-нодовую часть, UDP/XUDP, DNS, MRS, маршрутизацию и обновления на фактических устройствах.
5. Проверить Stash, sing-box, INCY, Happ, Shadowrocket и fallback XRAY_BASE64.
6. Только после проверки рассматривать `release/remnawave/srr.json`; при проблемах восстановить исходный SSR и шаблоны.

## Совместимость и миграция

`clients/` и `install/` сохраняются в качестве стабильных внешних точек входа. При миграции необходимо сверить реальные Subscription Response Rules, User-Agent клиентов, ссылки в Remnawave Shop и установленные приложения. Удалять старые URL можно только после подтверждения, что они больше не используются.

Никакая конфигурация не гарантирует неуязвимость к фильтрации или недоступности IP-сервера. Для отказоустойчивости нужны независимые доступные узлы. Платный Steal:443, его ключи и действующие подписки при работе с репозиторием не изменяются.

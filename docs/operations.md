# Эксплуатация и выпуск

## Проверки перед выпуском

Требуются Python 3.10+ и PyYAML, для проверки Mihomo — актуальное локальное ядро. Работать рекомендуется в отдельной копии репозитория.

```bash
python3 -m unittest discover -s tests -v
python3 scripts/audit_public_exposure.py
python3 scripts/audit_rules.py --check
```

Нативную конфигурацию Mihomo дополнительно проверяют с **синтетическими узлами** и временным каталогом: шаблон Remnawave содержит места вставки узлов и не предназначен для непосредственного запуска без их генерации. Тестируют 0, 1 и несколько узлов, загрузку всех MRS, DNS, отказ узла и отсутствие скрытого перехода внешнего трафика в DIRECT.

## Обновление правил

`scripts/refresh.py` обращается к внешним источникам и **изменяет файлы** после проверки данных, поэтому его следует запускать сначала в отдельном рабочем каталоге с резервной копией и проверкой diff. Он также обновляет совместимые URL и манифесты для старых клиентов.

```bash
python3 scripts/refresh.py
python3 scripts/audit_rules.py --check
```

Далее пересобираются MRS:

```bash
python3 release/mihomo/build.py --core /path/to/mihomo \
  --source-root . --output /tmp/garasu-mrs-next \
  --source-commit YOUR_COMMITTED_SOURCE_SHA
```

Проверяются SHA-256, число правил, корректность `format: mrs`, URL каждого провайдера и загрузка в реальном ядре. Нельзя публиковать MRS от другого снимка исходных списков. Ветка `dev` предназначена для разработки и проверки, а `main` — для утверждённых выпусков. Профили разработки ссылаются на `dev`; при выпуске ссылки необходимо перевести на `main` или конкретный проверенный коммит после тестирования.

GitHub Actions для обновления и публикации не используются в рефакторинговой ветке. Автоматическая регенерация исходных файлов и бинарных MRS вне GitHub Actions пока не настроена; клиентские интервалы обновления не заменяют сборку новых данных на сервере.

## Remnawave

Шаблоны в панели должны быть установлены отдельно; коммит в GitHub не меняет шаблоны, хранящиеся в Remnawave.

1. Экспортировать действующие SSR, шаблоны и настройки подписки.
2. В текущей панели шаблон MIHOMO называется `Default`. Для теста создать отдельный шаблон с именем `Garasu` и только затем направить на него тестовое SSR-правило; либо проверить уже существующий `Default` без замены платных подписок. Не указывать в SSR несуществующее имя шаблона.
3. Проверить выдачу на выделенной тестовой подписке через `release/remnawave/srr-test.json` и User-Agent `garasu-test-mihomo`.
4. Проверить персональную VLESS/REALITY-нодовую часть, UDP/XUDP, DNS, MRS, маршрутизацию и обновления на фактических устройствах.
5. Проверить Stash, sing-box, INCY, Happ, Shadowrocket и fallback XRAY_BASE64.
6. Только после проверки рассматривать `release/remnawave/srr.json`; при проблемах восстановить исходный SSR и шаблоны.

## Подключение дополнительной ноды без потери ручного выбора

1. Убедиться, что новая Node подключена, ее Inbound активирован в Config Profile, а Host включён, видим и имеет корректный адрес. Проверка зелёного статуса одной Node недостаточна.
2. В **Internal Squads** включить соответствующий Inbound для сквада тестового пользователя. В **External Squads** задаются другие шаблоны и заголовки, а не доступ к самому Inbound.
3. Прочитать тестовую подписку с настоящим User-Agent Mihomo и проверить, что оба Host присутствуют в массиве `proxies`. Если нода отсутствует, исправлять права/Host, а не переставлять группы в YAML.
4. Использовать `Garasu` как единственный видимый `select`; `Garasu Auto` — скрытая `url-test` с `include-all: true`. Remnawave добавляет разрешённые узлы в `Garasu`, поэтому на этой группе **не** должно быть `remnawave.include-proxies: false`.
5. Убедиться, что по умолчанию выбран `Garasu Auto` и что ручной выбор конкретного узла сохраняется. Ручной выбор отключает автоматическое переключение до возврата на Auto.
6. Проверить доступность HTTPS-адреса подписки с клиентской сети отдельно от доступности VLESS-ноды. Если у HTTPS-подписки и VPN один IP, отказ сети до него может нарушить и обновления, и соединение.
7. Только затем разворачивать изменения на другие сквады/подписки. Не изменять production SQL напрямую и не перезапускать платные узлы ради этого теста.

## Совместимость и миграция

`clients/` и `install/` сохраняются в качестве стабильных внешних точек входа. При миграции необходимо сверить реальные Subscription Response Rules, User-Agent клиентов, ссылки в Remnawave Shop и установленные приложения. Удалять старые URL можно только после подтверждения, что они больше не используются.

Никакая конфигурация не гарантирует неуязвимость к фильтрации или недоступности IP-сервера. Для отказоустойчивости нужны независимые доступные узлы. Платный Steal:443, его ключи и действующие подписки при работе с репозиторием не изменяются.

## Правило веток

В GitHub используются две постоянные ветки: `dev` и `main`. Все изменения сначала попадают в `dev`, где выполняются статические, нативные и интеграционные проверки. Перенос в `main` выполняется только после проверки Remnawave и совместимости с действующими подписчиками. Рабочие изменения в `main` напрямую не вносятся. Старые ветки должны удаляться только после сохранения их истории и проверки опубликованных ссылок.

### Выявлено в текущей панели

Правила MIHOMO раньше ссылались на шаблон `Garasu`, которого в базе нет. Фактически установленный шаблон называется `Default` и содержит одну видимую группу `Garasu` (select) со скрытой `Garasu Auto` (url-test). В `dev` SRR скорректированы на `Default` для воспроизводимости. На Mac может оставаться старый локальный профиль, когда адрес подписки по TCP недостижим. Не путать с доступностью VLESS-ноды: ключ/Short ID/SNI нового сервера совпадают с конфигурацией панели, но сам VLESS-сеанс не установлен даже через независимый SSH-маршрут. Нужны логи фактически запущенного Xray/RemnaNode на новом сервере; клиентскую настройку вручную считать проверенной отдельно.

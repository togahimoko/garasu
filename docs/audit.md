## Открытые риски — не считать выпуск завершённым

**Высокий приоритет**

- **Миграция из Remnawave не проверена.** Не сверены фактические SRR, имена сохранённых шаблонов и клиентские User-Agent у платных пользователей. Нельзя переключать полный `srr.json` без проверки.
- **Профили разработки ссылаются на ветку `dev`.** Перед выпуском в `main` URL должны быть перенесены на согласованный выпуск или зафиксированный коммит; действующие ссылки нельзя удалять без миграции.
- **Сборка MRS не автоматизирована.** Клиент обновляет бинарники по URL, но новые бинарники не появляются после редактирования исходного `.list` автоматически. GitHub Actions удалены; требуется отдельный согласованный механизм обновления.

**Средний приоритет**

- Не выполнен нативный импорт в INCY, Happ, Shadowrocket, Stash и sing-box на устройствах. Статическая проверка JSON не равна успешному запуску клиента.
- Не подтверждён холодный старт без кеша на ограниченных сетях, в том числе доступность GitHub Raw по DIRECT.
- Плавание TCP-доступности Steal через конкретного провайдера не решается рефакторингом репозитория. Обход IP/маршрутных ограничений нельзя гарантировать одними правилами.
- Старые `clients/` и `install/` технически необходимы до миграции: полностью убрать дублирующую доставку сейчас нельзя без риска для подписчиков.

### Первопричины

1. **Нет права на второй Inbound.** Зеленая нода не равна доступному Host у конкретного пользователя: инбаунд должен входить в его Internal Squad. Чтобы открыть второй Host пользователям, необходимо разрешить новый Inbound в их соответствующих сквадах. Без этого нода отсутствует даже в исправленном YAML.
2. **Старый тип основной группы.** URLTest выбирал сервер автоматически и не давал выбирать произвольную ноду вручную. Исправлено **только в `dev`**; панель Remnawave пока выдаёт старый шаблон.
3. **Точка подписки недоступна по домашнему TCP-маршруту.** Это препятствует обновлению состава узлов в клиенте даже после исправления прав. Проверка TLS-сертификата на сервере ранее проходила; ошибки `tls handshake eof` сами по себе не доказывают неправильный сертификат.

### Безопасный порядок внедрения

1. Проверить, что тестовый пользователь принадлежит Internal Squad с новым Inbound; не менять права всех платных пользователей без отдельного теста.
2. Убедиться, что персональная подписка с User-Agent Mihomo отдаёт два VLESS-узла.
3. Создать/обновить отдельный тестовый шаблон из `release/mihomo/config.yaml`, проверить, что выдаётся Selector + URLTest, а имена узлов соответствуют индивидуальным правам.
4. Проверить ручной выбор обоих узлов, автоматический выбор, DNS, TCP и доступ к внешним сайтам с домашней сети и мобильной сети.
5. После успешного теста расширить Inbound на нужные Internal Squads, переключить шаблон постепенно, сохранив резервную копию действующих SSR и шаблонов.
6. Обеспечить независимую доступность HTTPS-подписки при сетевой недоступности конкретной VPN-ноды. DNS-замена без работающего origin сама по себе проблему не решает.

**Статус:** исправление Selector проверено в `dev`; пользовательские права доступа и активный шаблон Remnawave в production **не изменены**. Полная эксплуатационная проверка должна закончиться после контролируемого включения второго Host.

## Критерии переноса в основную ветку

1. Проверить действующие SRR, сохранённые шаблоны Remnawave и их реальное использование.
2. Перевести тестового подписчика на `release/`, проверить персональный состав узлов, DNS, маршруты и автообновление.
3. Проверить всё семейство клиентов нативно, включая переключение Wi-Fi/мобильной сети и недоступность VPN.
4. Решить обновление MRS и источников без нежелательных GitHub Actions.
5. Обновить ссылки с `dev` на утверждённый адрес релиза; повторить тесты и только затем переносить изменения в `main`.

Статический аудит репозитория и тестовый runtime завершены; эксплуатационный аудит всех реальных клиентов и панели Remnawave остаётся отдельным обязательным этапом.

## Дополнительный аудит новой ноды и подписки

Последняя проверка 4 ноября 2026 (всё без изменения production).

- В активном профиле Mac имеются **две ноды** — `Steal` и `newCzech`. Но его видимая группа всё ещё `Garasu: url-test`; локальная подписка не обновилась до серверного `Garasu: select`.
- Серверное правило MIHOMO ссылалось на **не существующий** шаблон `Garasu`, тогда как в фактической БД установлен `Default`. Согласно Remnawave отсутствующий шаблон заменяется Default. В `dev` ссылки MIHOMO SSR скорректированы на существующий `Default` без воздействия на production.
- Серверный шаблон `Default` уже содержит `Garasu: select` и скрытый `Garasu Auto: url-test`. При успешном запросе сервер выдавал эту новую структуру; Mac ранее сохранял старый вариант, так как доступ к HTTPS-подписке с домашней сети нестабилен.
- У новой ноды DNS разрешается и TCP:443 подключается. Но реальная VLESS/REALITY-сессия на контрольный HTTPS-сайт завершается тайм-аутом **как напрямую**, так и через отдельный SSH-туннель через другой VPS. Пробы со значениями TLS fingerprint `firefox`, `chrome`, `safari` также не прошли.
- Публичный ключ REALITY, short ID и SNI выданного клиента совпадают с конфигурацией inbound, хранящейся в Remnawave. Соответствие активного профиля и привязки inbound к `newCzech` подтверждено. Это **не подтверждает**, что работающий процесс Xray новой ноды загрузил эту же конфигурацию. Удалённый SSH к новому узлу не авторизован; логи его фактического runtime не прочитаны.
- Для немедленной **локальной** проверки ручного выбора на Mac создан файл `~/Documents/Garasu-manual-switch.yaml` с разрешениями 0600 и двумя персональными нодами, собранный из уже загруженного профиля. Нативная проверка Mihomo пройдена. Файл **не публиковался в GitHub** и не назначен активным профилем; после импорта сам по себе не получит новые узлы при обновлении удалённой подписки.
- Контрактный тест SRR после исправления: **78/78 PASS**, сканирование публичных конфигураций на секреты: PASS.

**Незавершённое:** проверка реального сервера `newCzech` по его логам Xray/RemnaNode и источнику конфигурации; восстановление доступа Mac к URL подписки для автоматического обновления; тестовое применение действующего `Default`-шаблона без перезаписи платных настроек.

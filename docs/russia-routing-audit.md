# Garasu — жёсткий аудит маршрутизации для сетей РФ

Дата проверки: **4 ноября 2026**. Область: публичные правила, GeoSite/GeoIP, клиентские шаблоны и механизм обновления. **Никаких изменений нод, Remnawave и персональных подписок.**

Весь статический анализ воспроизводим через `scripts/audit_route_coverage.py` и `scripts/audit_geodata.py`. Данные взяты из текущего снимка `DigneZzZ/routing` с SHA `82d104cde92b271f545e1f61a61b1acd079e0aa7`; на момент проверки это был актуальный upstream-коммит (2026-11-04 03:04 UTC).

## Короткий вердикт

**Структура источников корректная, но политику маршрутизации нельзя считать завершённой.** Для безопасного выпуска нужно устранить зависимость широкого российского DIRECT от сетевой загрузки больших списков, согласовать объявленные и реальные DIRECT/REJECT-исключения и проверить DNS на российских сетях. Сам факт зелёного сервера, успешного ping или прохождения синтаксических тестов этого не доказывает.

## Как строят похожие решения

| Проект | Существенный подход | Что полезно для Garasu |
| --- | --- | --- |
| [DigneZzZ/routing](https://github.com/DigneZzZ/routing) | Отдельные **Lite/Full** для ПК и мобильных устройств; в Full доступны исключения РКН и широкий RU DIRECT, Lite осторожно отправляет неизвестные RU-домены через VPN | Две разные политики для разных условий надёжности, а не один тяжёлый шаблон для всех |
| [itdoginfo/allow-domains](https://github.com/itdoginfo/allow-domains) | Различает блокировки **из России** и российские сервисы, требующие российского IP **из-за границы** | Не смешивать «заблокировано провайдером» с «сервис не пускает зарубежный IP» |
| [enkinvsh/dropweb-mihomo](https://github.com/enkinvsh/dropweb-mihomo) | Приоритеты для Telegram/Discord/Meta, отдельные игровые и прямые сервисы; QUIC/UDP-443 блокируется с исключениями выше правила | UDP/QUIC нельзя ломать глобально без проверки голосовой связи, игр и мобильных приложений |
| [Aligotr/rule-set-ru](https://github.com/Aligotr/rule-set-ru) | Публикация отдельного прямого, проксируемого и блокируемого наборов в нескольких форматах | Проверка эквивалентности **результирующих решений**, а не одинаковых имён файлов |

Это архитектурные сравнения, **не** разрешение автоматически копировать чужие правила: у них разные цели, версии клиентов, исключения и доверенная база источников.

## P0 — отказ при отсутствующих списках РКН

Сейчас основной Mihomo-шаблон совмещает:

- полный набор `rkn-domains` (75 306 записей) и `rkn-ips` (25 391);
- удалённые HTTP rule-provider'ы;
- `DOMAIN-SUFFIX,ru,DIRECT` и аналогичные российские TLD;
- загрузку rule-provider'ов по GitHub Raw через `DIRECT`.

**Нативный отрицательный тест:** на чистом временном Mihomo 1.19.33 все 13 provider URL указывали на заведомо недоступный локальный порт, кеш был пуст. Ядро успешно запустилось; API показал `ruleCount: 0` для всех 13 наборов, а `DOMAIN-SUFFIX,ru,DIRECT` продолжало присутствовать в таблице маршрутов.

Последствие: без загруженного списка блокировок широкий DIRECT не имеет защитного исключения для соответствующего RU-домена. **Риск fail-open подтверждён архитектурно; фактическая утечка конкретного соединения отдельно не доказана.**

Обязательное решение:

1. Режим **Lite**: неизвестные домены (включая RU) по умолчанию идут в VPN; DIRECT — локальная сеть и строго отобранные российские сервисы. Lite не требует полного RKN для безопасности.
2. Режим **Full**: широкий RU DIRECT допускается только при готовом, проверенном и локально доступном полном наборе RKN; запуск/импорт должен явно отказать при отсутствии этих данных. Просто добавить `rule-provider` в конфиг **недостаточно**.
3. Проверить реальные последствия «нет кеша / не работает GitHub Raw / обновление прервано / повреждён MRS». Успешный `mihomo -t` не считается доказательством присутствия данных.

**Не рекомендуется** молча заменять Full на Lite для действующих подписчиков без проверки: это заметно изменит IP выхода для многих российских сайтов.

## P1 — объявленные действия отличаются от действующих

Доменный анализ применял текущие правила первых совпадений к опубликованным наборам. Он не подменяет фактическое DNS-разрешение или IP-классификацию.

| Набор | Исходных записей | Ожидаемое действие по политике | Что увидели в Mihomo |
| --- | ---: | --- | --- |
| `direct` | 3 284 | DIRECT | 3 206 направляются через PROXY |
| `games` | 117 | DIRECT | 116 направляются через PROXY |
| `ads` | 1 221 | REJECT | 117 направляются через PROXY |
| `rkn-domains` | 75 306 | PROXY | 75 306 — PROXY |
| `youtube` | 176 | PROXY | 176 — PROXY |

Причины: `direct` и `games` публикуются и загружаются, но не участвуют в фактических правилах Mihomo/Stash/Shadowrocket/sing-box. `ads` стоит после RKN, и его 117 записей перехватываются раньше.

**Не включать весь `direct` вслепую**: в 3 284 записях много международных Apple/Microsoft/игровых доменов и обратных DNS-зон. Без ревью их перенос в DIRECT раскроет пользовательский IP нежелательным получателям или нарушит доступность сервисов через VPN.

**Не поднимать `games` выше РКН**: в реестре встречаются Roblox, Valorant и другие игровые домены. Более высокая приоритетность игр может направить заблокированные ресурсы напрямую. Если нужны игры без VPN, следует определить конкретный разрешённый набор и проверить каждую конфликтную запись.

Для `ads` нужна явная продуктовая политика: если это обязательная блокировка, REJECT должен быть выше всех маршрутов на те же домены; если отдельные адреса нельзя блокировать без поломки приложений, такие исключения следует фиксировать **точечно**, а не отдавать предпочтение всему реестру автоматически.

## P1 — DNS и обновление списков

В Mihomo для обычного DNS используются DoH Google и Cloudflare, для разрешения доменов нод и прямых выходов — `system`. При этом MRS загружаются с GitHub Raw через DIRECT.

Проверить три независимых механизма:

1. **Bootstrap ноды:** домен сервера должен разрешаться без уже установленного прокси, иначе возникает циклическая зависимость.
2. **DNS-назначение:** внутренние имена и российские сервисы должны получать подходящие локальные ответы; внешние имена нельзя бездумно направлять через ненадёжные резолверы. Перевод всего DNS через VPN без bootstrap опасен.
3. **Доставка правил:** GitHub Raw, DNS и CDN не гарантированно доступны через каждого российского провайдера. Отказ доставки не должен менять маршрутизацию неизвестного домена на DIRECT.

[Официальная документация Mihomo](https://wiki.metacubex.one/en/config/dns/) различает `proxy-server-nameserver`, `direct-nameserver`, `nameserver-policy` и `respect-rules`. Параметры нельзя считать взаимозаменяемыми.

[Cloudflare в 2026 году](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/) отдельно предупреждает о систематическом замедлении доступа из российских сетей; поэтому проверка доступности одного `generate_204` и «ping ноды» недостаточны для подтверждения нормальной работы больших сайтов или загрузок.

## P1 — расхождения между клиентами

Статическая модель Mihomo, Stash, Shadowrocket и sing-box обнаружила **95 различий** на проверенных нероссийских доменах, главным образом в обратных DNS-зонах `.arpa`: Shadowrocket направляет их напрямую, остальные — через маршрут по умолчанию.

INCY/Happ и Xray нельзя объявлять эквивалентными на основании этих же 95 случаев: они используют GeoSite/GeoIP, другую модель DNS и другой порядок правил. Фактический полный список в `geo/geosite.dat` уже проверен через декодирование бинарных категорий:

- `BANNED-RU` — 75 306 и точное совпадение с текстовым RKN;
- `BLOCKED-RU` — 25 391 и точное совпадение с CIDR;
- `RU` — 25 157 и точное совпадение с CIDR;
- `GARASU-ADS` — 1 107 против 1 221 в основном текстовом наборе: 119 текстовых отсутствуют в бинарном и 5 дополнительных присутствуют только в бинарном.

Все GeoSite/GeoIP-категории, упоминаемые в исследованных INCY/Happ/Xray-шаблонах, существуют в бинарных файлах. Но наличие категории — **не** тест маршрута на реальном клиенте.

## P2 — производительность и мобильные клиенты

Текущие данные на диске: GeoSite **2 217 740 байт**, GeoIP **1 049 786 байт**; MRS в сумме около **762 КБ**. Размер на диске не равен размеру в памяти после загрузки и индексации.

Автор DigneZzZ отдельно использует облегчённые мобильные наборы и исключает лишние process-правила из iOS-профилей. Для Garasu стоит испытать Lite с минимальным curated DIRECT и без лишних категорий, прежде чем включать полноразмерную конфигурацию в ограниченное iOS network extension. Никаких обещаний экономии памяти без профилировки.

В sing-box 1.14 появился `initial_path` для локального первого запуска правил, а старые опции DNS-кеша меняются; перед миграцией проверить на настоящем ядре. Документация: [rule-set](https://sing-box.sagernet.org/configuration/rule-set/) и [migration](https://singbox.ai/wiki/migration/index.html).

## Рекомендуемый порядок внедрения

1. **P0:** спроектировать и испытать fail-safe Lite; Full с обязательной проверкой загруженности RKN. Ни одно изменение живого профиля без нативного теста.
2. **P1:** подготовить небольшую ревьюированную категорию критически важных RU-сервисов и отдельную политику игр; не использовать необработанные 3 284 `direct`-записи.
3. **P1:** зафиксировать политику `ads` и конфликтов с blocked; добавить тесты на несколько реальных доменов из пересечений.
4. **P1:** проверить DNS, cold-start, потерю доступа к GitHub Raw, отключение и восстановление VPN, Wi‑Fi/мобильную сеть на двух разных российских провайдерах.
5. **P2:** обеспечить эквивалентность решений по ключевым сценариям между Mihomo/Stash/Shadowrocket/sing-box/INCY/Happ/Xray, учитывая особенности каждой реализации.
6. **P2:** документировать и протестировать профиль для памяти мобильных устройств и порядок ручной публикации обновлённых списков.

**Выполнено в текущем аудите:** статическая проверка всех доменных категорий, содержимого .dat, исходников и контрольных сумм; нативный отрицательный тест холодного запуска. **Не выполнено:** фактические E2E-тесты каждого мобильного клиента и различных сетей РФ, захват реального DNS-трафика, разрешение лицензионных вопросов сторонних источников.

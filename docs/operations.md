# Эксплуатация и выпуск

## Проверки перед выпуском

Единая команда: `python3 scripts/qa.py --branch main`; при изменении правил выполнить `python3 scripts/sync_universal_routing.py --write`, затем `python3 scripts/sync_public_links.py --write` для синхронизации production-ссылок, мобильных aliases и манифеста; с установленным ядром Mihomo: `python3 scripts/qa.py --branch main --core /path/to/mihomo`. Подробный [чек-лист выпуска](release-checklist.md).


Требуются Python 3.10+ и PyYAML, для проверки Mihomo — актуальное локальное ядро. Работать рекомендуется в отдельной копии репозитория.

```bash
python3 -m unittest discover -s tests -v
python3 scripts/audit_public_exposure.py
python3 scripts/audit_rules.py --check
```

Нативную конфигурацию Mihomo дополнительно проверяют с **синтетическими узлами** и временным каталогом: только в тестовом процессе HTTP-провайдеры заменяются проверенными локальными копиями. В опубликованных шаблонах остаются ссылки. Sing-box 1.14 проверяется дополнительным флагом `--singbox-core /path/to/sing-box`. Шаблон Remnawave не предназначен для самостоятельного запуска без подстановки узлов. Тестируют 0, 1 и несколько узлов, загрузку всех MRS, DNS, отказ узла и отсутствие скрытого перехода внешнего трафика в DIRECT.

## Обновление правил

`scripts/refresh.py` обращается к внешним источникам и **изменяет файлы** после проверки данных, поэтому его следует запускать сначала в отдельном рабочем каталоге с резервной копией и проверкой diff. Он также обновляет совместимые URL и манифесты для старых клиентов.

```bash
python3 scripts/refresh.py
python3 scripts/audit_rules.py --check
```

Далее пересобираются MRS:

```bash
python3 release/mihomo/build.py --core /path/to/mihomo \
  --source-root . --output /tmp/garasu-mrs-next \
  --source-commit YOUR_COMMITTED_SOURCE_SHA
```

Проверяются SHA-256, число правил, корректность `format: mrs`, URL каждого провайдера и загрузка в реальном ядре. Нельзя публиковать MRS от другого снимка исходных списков. Ветка `dev` предназначена для разработки и проверки, а `main` — для утверждённых выпусков. Опубликованные профили из `main` ссылаются на бинарные MRS и маршруты по стабильному пути `main/release/`. Перед переносом каждого нового выпуска необходимо повторять сверку URL, контрольных сумм и тесты.

GitHub Actions не используются. Задача macOS `launchd` настроена на интервал 21600 секунд, но публикация требует авторизованного Git push. Пока не проверен первый успешный цикл, нельзя утверждать, что свежие списки выходят автоматически каждые 6 часов.

## Remnawave

Шаблоны в панели должны быть установлены отдельно; коммит в GitHub не меняет шаблоны, хранящиеся в Remnawave.

1. Экспортировать действующие SSR, шаблоны и настройки подписки.
2. Убедиться, что в панели существуют именованные шаблоны `Default` для MIHOMO, STASH и SINGBOX; SSR сам шаблоны не создаёт.
3. Использовать только `release/remnawave/srr.json` с реальными User-Agent. Перед внедрением сохранить действующий SSR и проверить ответы существующей авторизованной подписки без изменения её прав.
4. Проверить персональные VLESS/REALITY-узлы, DNS, TCP, UDP/XUDP, маршрутизацию и обновления на фактических клиентах.
5. Проверить Stash, sing-box, INCY, Happ, Shadowrocket и fallback XRAY_BASE64. Для Shadowrocket правила устанавливаются отдельно managed-config.
6. После успешной проверки внедрить production SSR; при проблеме восстановить исходный экспорт. Публикация GitHub сама по себе Remnawave не обновляет.

## Подключение дополнительной ноды без потери ручного выбора

1. Убедиться, что новая Node подключена, ее Inbound активирован в Config Profile, а Host включён, видим и имеет корректный адрес. Проверка зелёного статуса одной Node недостаточна.
2. В **Internal Squads** включить соответствующий Inbound для сквада тестового пользователя. В **External Squads** задаются другие шаблоны и заголовки, а не доступ к самому Inbound.
3. Прочитать тестовую подписку с настоящим User-Agent Mihomo и проверить, что оба Host присутствуют в массиве `proxies`. Если нода отсутствует, исправлять права/Host, а не переставлять группы в YAML.
4. Использовать единственную группу `Garasu` типа **url-test** с `include-all: true`; ноды подставляются автоматически. Не создавать второй селектор.
5. Проверить автоматический выбор при одной и нескольких нодах и отсутствие падения внешнего трафика в DIRECT при пустой группе.
6. Проверить доступность HTTPS-адреса подписки с клиентской сети отдельно от доступности VLESS-ноды. Если у HTTPS-подписки и VPN один IP, отказ сети до него может нарушить и обновления, и соединение.
7. Только затем разворачивать изменения на другие сквады/подписки. Не изменять production SQL напрямую и не перезапускать платные узлы ради этого теста.

## Совместимость и миграция

`clients/` и `install/` сохраняются в качестве стабильных внешних точек входа. При миграции необходимо сверить реальные Subscription Response Rules, User-Agent клиентов, ссылки в Remnawave Shop и установленные приложения. Удалять старые URL можно только после подтверждения, что они больше не используются.

Никакая конфигурация не гарантирует неуязвимость к фильтрации или недоступности IP-сервера. Для отказоустойчивости нужны независимые доступные узлы. Платный Steal:443, его ключи и действующие подписки при работе с репозиторием не изменяются.

## Правило веток

В GitHub используются две постоянные ветки: `dev` и `main`. Все изменения сначала попадают в `dev`, где выполняются статические, нативные и интеграционные проверки. Перенос в `main` выполняется только после проверки Remnawave и совместимости с действующими подписчиками. Рабочие изменения в `main` напрямую не вносятся. Старые ветки должны удаляться только после сохранения их истории и проверки опубликованных ссылок.

### Выявлено в текущей панели

Правила MIHOMO раньше ссылались на шаблон `Garasu`, которого в базе нет. Актуальный шаблон Mihomo должен называться `Default` и содержать **одну** группу `Garasu` типа `url-test` без ручного selector. В `dev` SRR скорректированы на `Default` для воспроизводимости. На Mac может оставаться старый локальный профиль, когда адрес подписки по TCP недостижим. Не путать с доступностью VLESS-ноды: ключ/Short ID/SNI нового сервера совпадают с конфигурацией панели, но сам VLESS-сеанс не установлен даже через независимый SSH-маршрут. Нужны логи фактически запущенного Xray/RemnaNode на новом сервере; клиентскую настройку вручную считать проверенной отдельно.

## Проверка опубликованной ветки main

- Проверить, что `release/mihomo/config.yaml`, `release/stash/config.yaml`, `release/shadowrocket/config.conf` и `release/remnawave/srr.json` ссылаются на `main/release/`, а не на `dev` или удалённые промежуточные ветки.
- Проверить, что 35 MRS и 2 classical YAML скачиваются без работающей ноды, а sing-box 1.14 запускается и скачивает все 37 SRS в изолированном режиме.
- Установленные шаблоны Remnawave, права Internal Squads и маршруты до VPN-нод проверяются отдельно. Публикация GitHub-репозитория не доказывает работоспособность сети подписчиков.
